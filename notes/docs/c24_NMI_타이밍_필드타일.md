## 증상과 원인

사용자 세이브 mt2_c23_minimap_1~11: 2번까지 깨끗, 3번부터 필드 뱅크 114·107·84가 1~3바이트씩 늘어나며 손상
(들판 타일 `$5B` 점 무늬가 달라짐). 바뀐 값이 전부 **그 주소의 아래 바이트**(`+$1B2 ← $B2`).

- 화면이 켜진 채 렌더링 중에 `$2007`에 쓰면 PPU는 그때 버스의 주소(패턴을 읽는 중이면 CHR 주소)에 주소 아래 바이트를
  쓴다(실기·Mesen 동일). 원판은 CHR-ROM이라 무해, 우리는 CHR-RAM이라 영구 손상.
- 쓰는 곳: 원판 필드 스크롤 버퍼 쓰기 `$FBEE–$FBFD`(60~64바이트). 원판에서도 **260행 dot 106~274**에 끝나는 빠듯한 코드.
- 한글판은 NMI 앞(스프라이트 DMA 전) `$F8DB JSR $FFAA`에서 글자 큐·이름표 검사로 매 프레임 +17사이클, 이름표 업로드
  대기 중이면 W2 경로로 약 +110사이클 → 마지막 몇 바이트가 **사전 렌더 줄 dot 2~146**으로 넘침.
- 같은 넘침으로 이름표·속성 마지막 바이트가 제자리에 안 써져 스크롤 경계에 팔레트가 어긋난 칸이 남을 수 있다.

## 수정: 스크롤 경로는 원판과 사이클까지 같게

| 위치 | c23 | c24 |
|---|---|---|
| `$F8DB` | `JSR $FFAA`(검사 후 DMA+업로드) | `JSR $FC9D` (원판 DMA) |
| `$F8FE` 텍스트·레코드 출력 | `JSR $FA31` | `JSR $FFF4` → 업로드 → `JMP $FA31` |
| `$F904` `$0380` 작업 없음 | `LDA $03CA` | `JSR $FFAA` → 업로드 → `LDA $03CA; RTS` |

업로드 = 기존 `$FF8D`(bank31 `$C000` → W2 이름표 → `$DC00` 글자 1개). 필드 스크롤 프레임과 `$0373` 1회성 작업
프레임은 다음 프레임으로 미룬다. `$F917 JSR $F970`이 스크롤(`$2005`)을 쓰므로 그 뒤(모든 경로가 지나는 `$F920`)에는
두면 안 된다(시도했다가 스크롤·타이밍이 깨져 철회). `$0302` bit7은 음악 드라이버 동안의 NMI 재진입 방지 깃발.

## 검증

- 렌더링 중 `$2007` 쓰기: c23 세이브 6개 × 3000프레임 무작위 → **0건** (c23은 같은 조건에서 `$FBF4`에서 발생).
- 끝 상태 CHR: 세이브 3·5·6 × 시드 2 × 4000프레임 → c24 **0/6 손상**, c23 **4/6 손상**(필드 뱅크 84·106·107·114).
- 필드 스크롤 NMI 끝 시각이 원판과 같은 범위(260행 dot 107~276), 글자 업로드 프레임 최악 255행.
- 같은 세이브를 원판 롬과 c24에 올려 13개 시점 걸었을 때 이름표·속성 메모리 **완전 일치**.
- 회귀: c22·c23 검증, 이름표 21(기준을 「사전 렌더 쓰기 0」으로 변경 — 258~260행은 vblank 안), 두 슬롯 LOAD, 이름 5종, 조사, C4.
- verify_c23은 체크포인트를 번호가 아니라 화면 상태로 고르게 바꿈(NMI 타이밍이 원판과 같아져 난수·조우가 달라짐).

## 참고

- 화면 맨 위·아래 한 줄의 흰 띠(팔레트 어긋남)는 **원판도 똑같이** 만든다(위 비교에서 속성 메모리 일치). TV에서는
  오버스캔으로 가려지는 줄이라 Mesen에서 위아래 8줄 자르기를 켜면 보이지 않는다.
- 이미 손상된 세이브스테이트는 CHR째 저장돼 있으니 전원 → 인게임 LOAD.
- 에뮬레이터: Mesen·FCEUmm 정상, Nestopia는 그래픽 깨짐(사용자 보고). 헤더는 NES 2.0 매퍼 19 + **CHR-RAM 256KB** +
  배터리 8KB로, 실제 N163 카트에는 없던 구성이라 지원이 코어마다 다르다. 한글 글자를 CHR-RAM에 올리는 구조라 되돌릴 수 없다.
