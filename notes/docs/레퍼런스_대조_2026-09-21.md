# 여신전생 II 번역판 구조 대조와 다음 구현

2026-09-21. 사용자 요청에 따라 일본어 기준 롬, 보관된 중국어·영어·스페인어 롬,
Darrman의 공개 소스와 Pennywise/Tom 1.04 배포 설명을 대조했다.
이번 범위는 정적 구조 분석과 번역 원문 준비다. 전체 게임의 이벤트 해석과 플레이 검증은 아직 끝나지 않았다.

## 결론과 작업 방향

1. Darrman 소스는 포인터·제어코드·화면별 데이터 위치를 찾는 참고 자료로 쓴다.
   공개판 자체도 본편 대사 미번역인 초기판이므로 번역문이나 화면 처리를 그대로 정답으로 삼지 않는다.
2. 보관된 중국판은 원래 글꼴을 교체하는 방식이 중심이다. 늘어난 CHR 128 KiB는 전부 0이다.
   이 파일에서 대량의 한글 음절을 처리할 새 출력 엔진을 가져올 수는 없다.
3. Pennywise/Tom의 PRG 확장·텍스트 재배치·이름 칸 확장은 좋은 설계 참고다.
   하지만 보관된 영문 롬은 BPS가 요구하는 원본과 다른 일본판에 적용한 결과이므로,
   정상 영문 배포판의 실행 기준으로 사용하면 안 된다.
4. 초기 `임시/patch_runtime.py`의 `B8..BF` 한글 이스케이프 방식은 원작 `BA..BF` 이벤트 처리와 겹친다.
   원래 명령을 보존하는 인코딩·출력 경로가 우선이다.
5. 컴퓨터·마법·아이템·상태 관련 32개 문구를 새로 번역했다. 원본 제어코드 순서를 검사했으며
   아직 ROM에 넣지 않았다. 기존 복구 번역과 합쳐 이미 145종의 한글 음절을 쓰므로,
   고정 64/128자 글꼴 하나만으로 전체 번역을 처리하는 방향은 부족하다.

## 입력 파일과 구조

수치는 iNES 헤더를 읽은 값이다. CRC32는 별도 표시가 없으면 헤더를 포함한 파일 전체 기준이다.
재현 가능한 상세 값은 `결과/codex/references/audit.json`에 있다.

| 파일 | PRG | CHR | 매퍼 | 파일 CRC32 | 용도와 제한 |
|---|---:|---:|---:|---|---|
| 현재 일본어 원본 | 256 KiB | 256 KiB | 19 | `7F8D4BC6` | c01의 검증된 원본 |
| 보관 중국판 `0998...nes` | 256 KiB | 384 KiB | 19 | `E26427C3` | 정적 글꼴·메뉴 교체 참고 |
| 보관 Pennywise 영어판 | 512 KiB | 256 KiB | 19 | `A7242C76` | 잘못된 원본에 패치한 파일; 실행 판정 제외 |
| 보관 스페인어판 | 512 KiB | 256 KiB | 19 | `2A06E0A9` | 확장 구조 참고; 배포 원본 일치 여부 미확인 |

중국판의 원본 256개 CHR 1 KiB 페이지 중 달라진 것은
`2, 3, 4, 5, 6, 251, 252, 253, 254`의 9개다.
마지막 고정 PRG 8 KiB는 일본판과 같다. 추가 CHR 131,072바이트의 비영 바이트 수는 0이다.
텍스트 구간에도 변경은 있지만, 변경 바이트 수를 번역률로 계산하지 않는다.
이 결론은 현재 보관 파일에만 해당한다.

[README](https://github.com/Darrman/MT2_Translation/blob/3da3c784fbc219343b4716298709618d326548a6/README.md)는
2019년 0.1 초기판이며 본편·NPC·악마 대화가 미번역이고, 일부 전투 번역과 창 배치에 문제가 있다고 밝힌다.
번역 용어를 참고하더라도 일본어 원문으로 검수한다.

[Atlas/MT2.bat](https://github.com/Darrman/MT2_Translation/blob/3da3c784fbc219343b4716298709618d326548a6/Atlas/MT2.bat)의
`script1`, `script2` 삽입 호출은 주석 처리돼 있다.
Atlas는 변환표와 명시적인 포인터/삽입 범위를 사용한다. 예를 들어 전투/일반 시스템 문구는
`#CREATEPTR(Combat,"LINEAR",$A010,16)`, `#JMP($14254,$15C4B)`로 처리한다.
현재 일본판의 포인터 영역 `0x14010..0x14254`에는 290개 16비트 항목이 들어간다.
일부 추출 설정의 끝 주소를 그대로 항목 수로 해석하지 말고 실제 첫 문자열 위치와 맞춰야 한다.

CHR 영역에도 텍스트 배치 데이터가 있다. 사람 상태창 `0x7ECA4..0x7EE3C`,
악마 상태창 `0x7F028..0x7F1FC` 등이 해당하며, `$00,count`로 빈 칸을 압축하는 타일 배치다.
이를 대사 인코더나 순수 폰트 이미지로 처리하면 안 된다. 주소는 현재 일본판의 파일 오프셋이다.

## Pennywise/Tom의 해결 방식

1.04 배포 압축파일의 저자 설명을 `결과/codex/references/pennywise_readme.txt`로 보존했다.
저자 설명에 따르면 abcde/abw로 대사 안에 섞인 비문자 데이터를 처리해 추출했고,
PRG 확장 후 텍스트를 재배치했으며, 일부 CHR 저장 데이터도 PRG로 옮겼다.
따라서 전체 본문을 단순히 `FF`로 잘라 다시 넣는 방법은 피해야 한다.

악마·아이템 이름을 12자로 늘리고, 아이템/마법 목록을 한 줄 한 항목과 좌우 페이지 전환으로 바꿨다.
플레이어 이름은 8자에서 10자로 늘렸으며, 화면 공간과 RAM 확보에 따른 변경도 설명한다.
이것은 글자 수 확대가 이름 데이터뿐 아니라 목록·좌표·공유 코드까지 바꾸는 작업임을 보여준다.
이 항목은 저자 설명이며, 이번에 전체 기능을 직접 플레이 검증한 것은 아니다.

보관 파일에서 정적으로 확인한 구조는 다음과 같다.

- 원작 PRG의 상당 부분이 확장판 상위 32..63번 8 KiB 뱅크로 이동한다.
- 원작 물리 뱅크 7의 파서는 확장판 물리 뱅크 39에서 찾을 수 있다.
  CPU `$C211..$C247`의 분류 코드는 동일하다.
- `$C153`은 원작 `LDA $C1B2,X`에서 `JSR $F6A0`으로 바뀌었다.
  고정 뱅크 `$F671`에 새 텍스트 뱅크/주소 테이블이 있으며, 추가 레코드를 선택하는 코드가 있다.
- 원작 `$C1E2`의 `ASL A`는 `NOP`이다. 줄 좌표 배율에 영향을 주는 변경으로 보이며,
  실제 화면의 행간과 모든 호출 경로는 별도 검증이 필요하다.
- 공통 뱅크 로더 `$E000..$E0A9`와 NMI의 `$F8DB: JSR $FC9D`는 유지된다.
  이 구조 자체가 한글용 동적 글꼴 업로더를 제공하는 것은 아니다.

### 보관 영문 롬의 원본 불일치

| 검사 대상 | BPS 요구값 | 현재 값 |
|---|---|---|
| 원본 파일 CRC32 | `CBB8C4CC` | `7F8D4BC6` |
| 출력 파일 CRC32 | `E74E6DD4` | `A7242C76` |
| 패치 자체 CRC32 | `66992514` | 일치 |

수정 전 `참고/bps.py`의 디코더로 현재 일본판에 패치를 메모리상 적용하니,
보관된 영문 롬과 바이트 단위로 같았다. 출력 파일은 새로 쓰지 않고 비교했다.
기존 도구가 CRC 검사를 생략해 잘못된 원본도 처리한 것이 원인이다.
공식 패치 자체의 오류라고 판단한 것은 아니다.

배포 설명은 `Japan (Rev A)`를 요구한다. 현재 원본의 헤더 제외 CRC는 `10C9A789`이며,
참고 자료의 `96773F32`와 구분해야 한다. Mesen 데이터베이스에는 두 값 모두 등록돼 있다.
따라서 현재 일본어 기준 롬 자체를 손상 파일이라고 단정하거나 c01의 원본을 바꾸지 않는다.
보관 중인 인접 압축파일도 현재 원본과 같아, 올바른 Rev A 원본은 이번 검색에서 찾지 못했다.

`참고/bps.py`는 원본·패치·결과 CRC, 크기, 복사 범위를 검사한 뒤에만 결과를 쓰도록 수정했다.
원본 불일치, 패치 손상, 잘린 데이터, 대상 CRC 실패 및 네 가지 복사 동작을 다루는 테스트 6개가 통과했다.
정상 영문판 실행 대조를 재개할 때는 요구 CRC가 맞는 사용자 보유 원본이 필요하다.
그 전에도 현재 일본판의 한글화와 정적 소스 분석은 계속할 수 있다.

## 초기 한글 이스케이프와 이벤트 명령 충돌

`임시/patch_runtime.py`는 `$B8..$BF`를 한글 페이지 선택으로 소비한다.
그러나 원작의 `$C211` 분류부는 이 범위를 `$C221`로 보내고, 뱅크 호출을 통해
물리 PRG 뱅크 15의 CPU `$DB05` 처리기로 넘긴다.
그곳은 `SEC; SBC #$BA; ASL; TAX` 후 `$DB19`의 점프 테이블을 사용한다.

| 원작 코드 | 처리기 CPU 주소 |
|---|---|
| `BA` | `DB41` |
| `BB` | `DB5A` |
| `BC` | `DB25` |
| `BD` | `DB2C` |
| `BE` | `DB33` |
| `BF` | `DB3A` |

여러 처리기는 다른 이벤트 루틴을 호출한다. `BA..BF`를 빈 코드나 문자로 간주해
두 바이트씩 소비하면 원래 이벤트 흐름을 잃는다.
`B8/B9`의 유효 사용 여부와 모든 이벤트 인수 길이는 아직 조사 중이다.
이것은 남은 초기 소스에서 확인한 충돌이며, 모든 후속 실험판이 같은 오류를 가진다는 뜻은 아니다.

## 사용량을 고려한 후속 확인: v37·v40 파서

계정 조회 시 5시간 36%, 주간 13%가 남아 있어 이번 후속 작업은 정적 분기 확인으로 제한했다.
`python tools/audit_legacy_parser.py`는 원작·c01·v37·v40의 실제 명령 바이트를 읽어
입력값 256종을 각각 추적한다. CMP/분기/JMP 등 분류에 필요한 명령만 실행하며,
원작 처리기 또는 실험판 한글/대체 테이블 처리기 입구에 도달하면 멈춘다.
RAM·PPU·전체 이벤트를 실행하는 에뮬레이터 검증은 아니다.

결과는 `결과/codex/references/legacy_parser_audit.json`에 입력별 경로와 ROM 해시로 남겼다.

| 입력 | 원작·c01 | v37·v40 |
|---|---|---|
| `00..B7` 184종 | 원래 문자 반환 | 정상 문자 반환 |
| `B8/B9` | 원작 B8..BF 처리기 | 한글 이스케이프 |
| `BA..BF` 6종 | 원작 이벤트 처리 | 원작 이벤트 처리 유지 |
| `C3` | 원작 C0..DF 처리기 | 한글 이스케이프 페이지 2 |
| 나머지 `C0..DF` 31종 | 원작 이벤트 처리 | 대체 테이블 처리기로 분기 |
| `E0..FF` 32종 | 상위 처리 단계로 바이트 반환 | 같은 방식으로 반환 |

c01은 256종 모두 원작과 경로·반환값이 같다. v37과 v40의 분류기 바이트도 서로 같다.
초기 소스의 BA..BF 충돌은 두 실험판에서 이미 피해 갔다. 일반 문자의 BCC 대상은
`F75A: RTS`여서 정상이며, 바로 다음 `F75B: JMP C218`과 혼동하면 안 된다.

남은 문제는 `C3`다. 원작은 물리 PRG 뱅크 15의 `C681` 처리기로 보내고,
이 처리기는 `LDA #1; STA $0729; JSR $C03C` 등 실제 로직을 가진다.
두 실험판은 이를 `F712: LDA #2` → `F714`의 한글 처리로 보낸다.
원작 명령과 코드 공간이 겹치는 사실은 확정됐지만, 사용 중인 원작 C3 이벤트가
실험판에서 다른 코드로 모두 변환됐는지는 아직 확인하지 못했다.
본문/전투 포인터의 첫 바이트 및 단순 문자 접두부까지만 검사해서는 활성 C3 사례가 나오지 않았다.
따라서 이 단계에서 특정 이벤트가 실제로 고장 났다고 단정하거나 기계적으로 C3를 바꾸지 않는다.

초기화도 다르다. v37은 CHR-ROM 0인 NES 2.0 헤더와 `RESET=F671`을 쓰며,
추가 부팅 루틴이 있다. v40은 CHR-ROM을 가진 iNES 헤더와 원작 `RESET=F800`을 유지한다.
두 파일의 `F8DB`는 `JSR FF8A`로 바뀌어 NMI에서 뱅크 31의 업로더를 호출한다.
전체 업로더의 타일·시간·RAM 안전성은 이번 범위에 포함하지 않았다.

다음은 `F766` 대체 테이블과 본문 재배치 데이터를 함께 읽어 원작 C3 사용이 변환됐는지 확인하는 일이다.
검증된 c01을 유지하고, 이 제어코드 경계가 정리된 뒤 COMP 창의 한글 출력을 붙인다.

## C3 후속 대조 완료

`python tools/audit_c3_operands.py`로 원작 네 텍스트 블록에서 포인터 영역을 제외한
모든 C3 바이트를 조사했다. script1·combat에는 없고, script2에 8개, script3에 2개가 있다.
10개 모두 독립 C3 명령이 아닌 다른 이벤트의 인수다.
Darrman의 추출 원문과 일본어 ROM 바이트를 함께 확인했다.

| 이벤트 바이트 | C3의 위치 | 원작 사례 수 |
|---|---|---:|
| `D0 C3 01/02` | D0 첫 인수 | 2 |
| `C9 C3` | NPC 지정 인수 | 1 |
| `DD C3` | 변수 지정 인수 | 3 |
| `FA 05 C3` | 적 스프라이트 지정 인수 | 2 |
| `FA 4A C3` | FA 확장 이벤트 인수 | 1 |
| `DE C3` | 아이템 지정 인수 | 1 |

v37·v40 각각의 새 포인터를 따라 해당 메시지를 찾아 비교했다.
두 파일 모두 대응 메시지에 위 이벤트 바이트 패턴 10개가 보존돼 있다.
또한 원작 이벤트 처리 뱅크 15와 두 실험판의 대응 뱅크 47은 8 KiB 전체가 같다.
결과와 원본/재배치 주소는 `결과/codex/references/c3_operand_audit.json`에 있다.

`F766` 대체 테이블은 C3를 변환하는 테이블이 아니었다. 값이 있는 항목은
`CD→FF7E`, `CF→FF81`, `D8→FF84`, `D9→FF87`, `DB→FF7A`의 다섯 개이며,
짧은 문자열을 참조한다. 나머지는 원래 분기로 돌아가는 경로가 있다.
이 다섯 코드의 전체 호출 범위와 게임 실행은 별도 검증 대상이다.

확인한 네 본문 블록에서는 C3 충돌로 명령이 사라진 사례가 없으므로,
C3 바이트를 일괄 치환하거나 기존 인코딩을 즉시 폐기하지 않는다.
원작에는 독립 C3 처리기가 있지만 이번 블록들에서 호출 사례를 찾지 못했다.
이 결론은 모든 게임 데이터와 실행 경로에서 C3가 미사용이라는 증명은 아니다.

삽입 도구의 원칙을 확정한다. `B8/B9/C3` 한글 바이트는 문자 구간에서만 해석한다.
이벤트는 명령과 정해진 길이의 인수를 묶어 보존하고, 인수의 C3를 한글로 해석하거나 바꾸지 않는다.
가변 길이 이벤트도 있으므로 이 감사 스크립트를 전체 스크립트 파서로 쓰지 않는다.

다음 구현은 v37의 CHR-RAM 초기화와 NMI 업로더를 확인하고, 같은 롬으로 새로 부팅해
COMP 창에서 실제 글꼴 출력을 검증하는 단계다. 검증용 c01과 새 번역 32개는 그대로 보존했다.
