# c10 게임 내 저장 소실 수정

2026-09-26. 배포 ROM: `작업한 롬파일/mt2_codex_c10_savefix.nes`.
SHA256: `13539aef4822b294fc9c069d5d9166fd7c221d61b1a43146d05d7b827b76d4f5`.
패치는 `패치파일/mt2_codex_c10_savefix.ips`(일본어 원본용), `mt2_codex_c10_FROM_c09.ips`다.

## 확인된 원인

c08에서 옮긴 한글 캐시 `7F60..7FEB`와 c09의 추가 변수 `7FEC`가 원작의 저장 메모리 초기화 표식 `7FC0..7FFF`를 덮었다. 원작 F97E는 이 64바이트가 모두 FF인지 검사한다. 하나라도 다르면 F993에서 SRAM `6000..7FFF` 전체를 지운다. 플레이 중 상태창·전투 검사만으로는 이 부팅 경로를 확인하지 못했다.

제공된 c09 강제 세이브에서 저장 선택 → 파일1 선택 → 기록했습니다 → 배터리 파일 생성까지는 정상이다. 생성한 배터리 파일만 사용하여 새 프로세스로 c09를 부팅하면 F9A5에서 저장 슬롯 `6800..77FF` 4096바이트에 쓰기가 발생하고, `DDSII PRESENTED BY ATLUS` 서명이 0으로 지워진다. 일본어 원본은 같은 조건에서 기록을 유지한다. 사용자가 확인한 ‘저장 후 재실행하면 기록이 없음’과 일치한다.

## 수정

알려진 삽입 코드의 캐시 참조 118곳을 `6000..608C`로 옮겼다. 게임의 슬롯, 지도 버퍼, 사운드, 원래 초기화 표식은 건드리지 않는다. 절대 주소처럼 보이는 데이터까지 일괄 치환하지 않고 지정 코드 구간의 6502 명령 피연산자만 수정한다. ORA 절대 주소도 포함한다.

새 부팅 보조 코드 B9C0는 두 슬롯 중 하나라도 원래의 24바이트 서명이 정확히 일치하면 기존 표식을 FF로 복구한다. c08/c09가 기록했으나 아직 다음 부팅에서 지우지 않은 배터리 파일을 보존하기 위한 이행 처리다. 서명이 없는 새 메모리는 원작 초기화 경로를 그대로 사용한다. 캐시의 준비 상태는 매번 무효화한다.

이미 c09를 재실행하여 지워진 배터리 파일 자체를 복원했다고 주장하지 않는다. 사용자가 제공한 강제 세이브에는 진행 상태가 남아 있으므로, c10에서 강제 세이브를 불러온 후 게임 내 저장을 다시 하면 된다. 기존 사용자 ROM, .mss, .sav는 덮어쓰지 않았다. 파일명이 달라지면 Mesen은 다른 배터리 파일을 사용한다.

## 검증

- 두 게임 내 저장 슬롯을 기록한 뒤, 강제 세이브를 사용하지 않고 별도의 새 Mesen 프로세스에서 각각 LOAD했다.
- 슬롯1/2의 4096바이트가 부팅 전후 동일하며, 불러온 파일 번호·사용자 이름·파티 데이터가 저장값과 일치한다.
- 원작 표식 64바이트는 FF를 유지한다. 콜드 로드와 이어진 필드 실행에서 새 캐시 영역에 접근한 원작 코드가 없었다.
- 악마·종족·아이템·마법·선택지 382개 CPU/비트맵 검사 통과. c09 화면 581글자/37184픽셀과 영상 자막46글자 검사 통과.
- 12개 화면 시나리오에서 지정 글꼴 영역 밖 CHR 변경 0바이트. IPS 두 가지 적용 결과가 배포 ROM과 동일하다.
