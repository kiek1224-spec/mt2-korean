# c03: 상하 이동 그래픽 수정과 COMP 번역

## 결과와 적용 대상

- 실행 파일: `작업한 롬파일/mt2_codex_c03_scroll_comp.nes`
- 일본어 원본용 패치: `패치파일/mt2_codex_c03_scroll_comp.ips`
- c02 전용 갱신 패치: `패치파일/mt2_codex_c03_FROM_c02.ips`
- 출력 SHA256: `a45df80357fde1301a5bab2608b7f19876f260c2c11f26d4d5b1ebd27c9926c9`
- 기준 c01과 사용자가 제공한 두 세이브 원본은 덮어쓰지 않았다.

c01은 원작 그래픽 엔진을 쓰는 메뉴 기준판이다. c02는 v37의 256 KiB CHR-RAM과 동적 한글 업로더를 계승하므로 c01 세이브를 c02에 교차 적용해 판정하지 않는다. 이번 재현은 c02에 대응하는 사용자 세이브를 Mesen에 로드한 뒤 실제 게임 입력을 주어 수행했다.

## 원인과 수정

압축 해제된 v37 그래픽 256 KiB는 v40의 대응 CHR 데이터와 같았다. 화면 깨짐은 그래픽 원본 손상보다 NMI 처리 시간에 연결됐다. 기존 `F8DB: JSR FF8A`는 글꼴 전송 큐가 비어 있어도 뱅크 전환과 업로더를 거쳐 원래 OAM DMA보다 약 89 CPU 사이클을 추가했다.

원래 DMA로 바로 연결하면 동일 이동의 깨짐이 사라졌다. 여기에 지연만 추가한 대조군에서 원래 깨짐이 재현됐다. 플래그 보존은 개선하지 못했고, 뱅크 전환만 수행한 대조군은 정상 DMA와 일치했다. 이 결과는 NMI 안의 불필요한 지연이 스크롤 화면에 영향을 준다는 진단을 뒷받침한다. 정확히 어느 PPU 쓰기가 어느 dot의 마감을 넘는지는 별도로 계측하지 않았다.

c03은 CPU `FFAA`의 빈 공간에 14바이트 분기를 넣는다. `$013F`와 `$0140`이 같으면 원래 DMA `FC9D`로 바로 가고, 전송할 글꼴이 있으면 기존 `FF8A` 업로더를 실행한다. 빈 큐의 추가 비용은 14사이클로 줄어든다. ROM 파일 오프셋은 후크 `7F8EB`, 분기 `7FFBA`다.

업로더 전체를 끄는 롬은 원인 분석용이며 배포판이 아니다. 후크를 다른 NMI 위치로 옮기는 후보는 화면 차이가 커져 폐기했다. 해당 실험 파일들은 `결과/codex/experiments/`에 남아 있다.

## 실제 검증

`tools/verify_c03.py --emulator`는 다음을 재현하며 결과를 `결과/codex/c03_verification.json`에 남긴다.

1. 일본어 원본용 IPS와 c02 갱신 IPS가 같은 c03을 만드는지 검사한다.
2. c02 대비 변경이 NMI 후크·분기와 COMP 문구 영역 안에만 있는지 검사한다.
3. 제공된 c02 세이브에서 아래 32프레임, 위 32프레임의 입력과 대기를 포함한 67개 화면을 정상 DMA 대조군과 픽셀 단위로 비교한다.
4. A 입력으로 필드 메뉴와 COMP 창을 열고, 글꼴 큐가 소진됐는지 검사한다. `c03_final_comp/screen5.png`에서 새 문구를 직접 확인했다.
5. B 입력으로 두 창을 닫은 뒤 다시 67개 이동 화면을 같은 저장 상태의 정상 DMA 대조군과 비교한다.
6. 사용자 원본 세이브의 해시가 유지되는지 검사한다.

수정 전 c02는 첫 이동 67개 중 35개 화면에서 정상 DMA와 달랐다. 지연만 넣은 대조군도 같은 차이를 보였다. 최종 판정은 위 검증 JSON과 각 폴더의 raw 화면·입력 대본·Mesen 로그를 따른다. 비교 대상은 c01과 화면 내용이 다른 c02 지도이므로, 픽셀 검증에는 c02와 같은 그래픽을 쓰는 DMA 대조군을 사용했다.

## 한글화 진행

새 번역 32개 중 COMP 메시지 ID 3을 실제 삽입했다. 문구는 `컴퓨터 가동 / 소환 / 귀환 / 해제 / 순서 변경 / 메시지 속도`다. 제어코드 LINE 6개와 END를 보존하며 기존 53바이트 공간에 51바이트로 들어간다. 포인터나 후속 메시지를 옮기지 않았다.

`translations/v37_encoding_recovery.json`에 기존 글꼴 코드와 비트맵을 고정했다. 빌드는 외부 폰트를 다시 추출하지 않으며 동적 글꼴의 실제 바이트를 입력 롬과 대조한다. 32개 초안 전체의 105종 음절 중 104종에 대응 코드가 발견됐으므로 나머지 문구를 무조건 일괄 삽입하면 안 된다.

남은 31개 초안은 이번에 삽입하지 않았다. 기존 v37의 필드 메뉴 제목과 이름 표시는 별도 정리가 필요하다. 다음 작업은 이 고정 메뉴 영역의 글꼴과 타일 배치를 c01과 대조하고, 선택지별 COMP 동작과 전투 문구로 범위를 넓히는 것이다.

## 부팅과 한계

부팅 루틴은 이번에 바꾸지 않았다. v37 계열은 처음에 256 KiB 그래픽을 CHR-RAM에 풀어 넣으므로 c01보다 시작이 늦다. 이전 c02는 너무 이른 검정 화면 관찰에서 시작한 초기화 실험이며, 원래 v37도 기다리면 부팅하므로 c02를 검증된 부팅 속도 개선판으로 부르면 안 된다.

이번 검증은 제공된 지도와 COMP 창에 한정된다. 글꼴 큐가 계속 바쁜 상태의 모든 NMI 경로, 새 게임부터의 전체 플레이, 후반부·전투 전체가 검증된 것은 아니다. c03은 해당 재현 문제를 해결하고 COMP 번역을 시작한 시험판이다.

## 재현 명령

프로젝트 폴더에서 Python 3 및 Pillow, 인접한 Mesen 2.2.1을 사용한다.

```powershell
python tools/build_c03.py
python tools/verify_c03.py --emulator
```

현재 셸에 `python`이 없으면 로컬 Python 3를 사용한다. 각 시험은 고유한 임시 ROM 이름을 사용하고 기존 Mesen 설정을 저장하지 않는다.
